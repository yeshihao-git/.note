# 架构设计

**why**：
用于解决如何组织代码的问题

| 架构 / 方法             | 核心思想                         | 典型结构                                              | 适合场景            | 优点            | 缺点                    |
| ------------------- | ---------------------------- | ------------------------------------------------- | --------------- | ------------- | --------------------- |
| **单体架构**            | 所有功能放在一个应用中                  | 一个项目 → 多个模块                                       | 小型项目、个人项目、早期产品  | 简单、开发快、部署简单   | 项目变大后容易混乱             |
| **三层架构**            | 按技术职责分层                      | Controller → Service → DAO                        | CRUD 系统、后台管理系统  | 简单易懂、上手容易     | 业务复杂后容易出现 Service 巨型类 |
| **MVC**             | Model / View / Controller 分离 | Controller → Model → View                         | Web 应用、传统前后端项目  | 职责比较清晰        | 更关注表现层，不解决复杂业务建模      |
| **DDD**             | 围绕业务领域建模                     | Domain / Application / Infrastructure / Interface | **复杂业务系统**      | 业务逻辑清晰、适合长期维护 | 学习成本高、简单项目容易过度设计      |

## DDD

| 层                  | 中文理解  | 主要负责什么 | 典型代码                               |
| ------------------ | ----- | ------ | ---------------------------------- |
| **Interface**      | 接口层   | 对外接口   | Controller、DTO                     |
| **Application**    | 应用层   | 流程     | ApplicationService、UseCase         |
| **Domain**         | 领域层   | 业务     | Entity、Value Object、Domain Service |
| **Infrastructure** | 基础设施层 | 技术实现   | MySQL、Redis、MQ、HTTP Client         |

## 三层架构

```
┌─────────────────────┐
│  Presentation       │  表示层
│  Controller / API   │
├─────────────────────┤
│  Business           │  业务逻辑层
│  Service            │
├─────────────────────┤
│  Data Access        │  数据访问层
│  DAO / Repository   │
└─────────────────────┘
          ↓
       Database
```
