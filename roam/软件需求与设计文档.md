```

	  │
	  ▼

	  │
	  ▼

	  │
	  ▼
```

## PRD（产品需求文档）

**what**：PRD
单个文件。明确 产品要做什么、为谁解决什么问题、这一期做什么、做到什么程度算完成
```
1. 为什么做？
   → 产品背景、用户痛点、产品目标

2. 为谁做？
   → 目标用户、用户角色

3. 做什么？
   → 产品范围、功能需求、数据规则

4. 做到什么程度？
   → 业务规则、非功能需求、验收标准

5. 怎样提供给用户使用？
   → 页面、流程、交互和界面状态

6. 怎样确认完成并控制变化？
   → 验收发布、文档版本、审批和待确认事项
```
- ==负责人==：产品经理（PM） / 业务分析师（BA）

**how**：大纲
```
## 01 文档信息
文档版本、作者、编写日期、修订记录、审批状态。

## 02 产品概述
产品背景、产品定位、目标用户、用户痛点、产品目标。

## 03 产品范围
本期建设范围、不包含的功能、版本规划、项目约束。

## 04 用户角色与权限
用户类型、角色权限矩阵、不同角色的操作范围。

## 05 功能需求
功能模块、用户故事（US）、业务规则、异常与边界情况、验收标准（AC）。

## 06 数据与内容规则
需要保存的数据、数据可见性、数据生命周期、删除与保留规则。无需详细设计数据库表。

## 07 非功能需求
性能、安全性、可用性、兼容性、可维护性、无障碍要求等。

## 08 交互与界面要求
页面清单、页面跳转、关键交互、原型图及界面状态。

## 09 验收与发布要求
整体验收条件、上线标准、发布范围、已知限制。

## 10 附录及待确认事项
名词解释、待确认事项等...
```

### 相关术语
#### US（User Story）

**what**：
用户故事。描述用户的需求

```
US（用户故事）
 ├── FR（功能需求）
 ├── 业务规则（Business Rules）
 └── AC（验收标准）
```

#### FR（Functional Requirement）

**what**：
功能需求。具体的功能要求

**示例**：
```
FR-HOME-001 是一个功能需求的唯一编号，可以拆解为：
- FR：Functional Requirement，功能需求
- HOME：Home，所属模块为首页
- 001：该模块下的第 001 条需求
```

#### NFR（Non-Functional Requirement）

**what**：
非功能需求

#### AC（Acceptance Criteria）

**what**：
验收标准。验证需求是否实现

## 需求基线

**what**：
不是单独一个文件，而是一个文件包。PRD 经过相关人员评审并正式确认的需求版本，后续开发、测试和变更都以它为依据
```
个人博客网站 V1.0 需求基线
├── 01-个人博客网站PRD-V1.0.md
├── 02-需求评审记录.md
├── 03-需求追踪矩阵.xlsx
├── 04-已确认原型图
├── 05-待确认及延期事项.md
└── 06-基线确认单.md
```
- ==负责人==：产品经理（PM） / 业务分析师（BA）

## SPEC（规格说明书）

**what**：Spec
规格说明书（功能规格），侧重技术与实现逻辑，它回答 how
- ==负责人==：业务分析师（BA） / 系统分析师 / 开发人员

## 设计文档

| 关键词                       | 主要回答什么问题        |   是否重要 |
| ------------------------- | --------------- | -----: |
| **Background 背景**         | 为什么要做？          |    ⭐⭐⭐ |
| **Goal 目标**               | 做完以后达到什么效果？     |    ⭐⭐⭐ |
| **Scope 范围**              | 做什么、不做什么？       |    ⭐⭐⭐ |
| **Requirement 需求**        | 系统需要满足什么？       |   ⭐⭐⭐⭐ |
| **Architecture 架构**       | 整体系统怎么组成？       |  ⭐⭐⭐⭐⭐ |
| **Module 模块**             | 系统拆成哪些模块？       |  ⭐⭐⭐⭐⭐ |
| **Flow 流程**               | 数据/业务怎么流转？      |  ⭐⭐⭐⭐⭐ |
| **Data 数据模型**             | 数据怎么存？表怎么设计？    |  ⭐⭐⭐⭐⭐ |
| **API 接口**                | 模块之间怎么通信？       |   ⭐⭐⭐⭐ |
| **Design Decision 设计决策**  | 为什么这样设计？        |  ⭐⭐⭐⭐⭐ |
| **Error 异常**              | 出问题怎么办？         |   ⭐⭐⭐⭐ |
| **Security 安全**           | 怎么认证、授权、保护数据？   |   ⭐⭐⭐⭐ |
| **Performance 性能**        | 性能瓶颈和指标是什么？     |    ⭐⭐⭐ |
| **Concurrency 并发**        | 多人/多请求同时操作怎么办？  |   ⭐⭐⭐⭐ |
| **Transaction 事务**        | 如何保证数据一致性？      |   ⭐⭐⭐⭐ |
| **Logging 日志**            | 出问题怎么排查？        |    ⭐⭐⭐ |
| **Monitoring 监控**         | 怎么发现系统异常？       |    ⭐⭐⭐ |
| **Risk 风险**               | 有什么风险和限制？       |   ⭐⭐⭐⭐ |
| **Trade-off 权衡**          | 为什么选 A 而不是 B？   |  ⭐⭐⭐⭐⭐ |
| **Test 测试**               | 怎么验证设计正确？       |   ⭐⭐⭐⭐ |
